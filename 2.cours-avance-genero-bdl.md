# Cours Avancé Genero BDL : Du Développeur Intermédiaire (Middle) à l'Architecte (Senior)

Ce cours d'ingénierie logicielle prolonge l'apprentissage des bases de Genero BDL (*Business Development Language*). Conçu pour accompagner les développeurs souhaitant franchir un cap professionnel, ce document aborde les mécanismes avancés de gestion des interactions, les transactions SQL complexes, la modularité enterprise, la manipulation dynamique de l'IHM via l'AUI (*Abstract User Interface*), les architectures SOA RESTful et les pratiques d'optimisation en environnement de production.

---

## Partie 1 : Niveau Intermediate (Middle Developer)

La maîtrise du niveau intermédiaire exige de dépasser la simple saisie écran/base de données mono-enregistrement pour orchestrer des flux métiers complexes, des listes interactives et des accès concurrents sécurisés.

### 1. Interaction Utilisateur Avancée & Multi-Dialogues

Les applications de gestion d'entreprise s'articulent principalement autour de listes dynamiques, de formulaires de recherche (*Query-By-Example*) et de fenêtres maîtresses-détails.

#### 1.1 Listes Interactives et Saisie en Tableau (`DISPLAY ARRAY` & `INPUT ARRAY`)

Alors que `DISPLAY` et `INPUT` gèrent un enregistrement unique, les instructions `DISPLAY ARRAY` et `INPUT ARRAY` lient des tableaux dynamiques de programmes (*Program Arrays*) à des conteneurs visuels de type `TABLE` ou `MATRIX` définis dans le fichier de formulaire (`.per`).

- **`DISPLAY ARRAY`** : Permet la navigation, le tri, la recherche et la sélection au sein d'une liste de données en lecture seule (ou modifiable via des actions spécifiques).
- **`INPUT ARRAY`** : Active la saisie directe, l'ajout, la modification et la suppression de lignes dans une grille.

```4gl
-- Exemple de gestion complète d'une grille de commandes avec INPUT ARRAY
FUNCTION edit_order_items(p_order_id INT)
    DEFINE l_items DYNAMIC ARRAY OF RECORD
        item_num INT,
        product_id INT,
        quantity INT,
        unit_price DECIMAL(10,2),
        total_price DECIMAL(10,2)
    END RECORD
    DEFINE l_idx INT

    CALL load_order_items(p_order_id) RETURNING l_items

    INPUT ARRAY l_items FROM s_items.*
        ATTRIBUTES(INSERT ROW = TRUE, DELETE ROW = TRUE)

        BEFORE INPUT
            MESSAGE "Saisie des lignes de commande..."

        BEFORE ROW
            LET l_idx = arr_curr()
            -- Calcul automatique du prix total de la ligne
            LET l_items[l_idx].total_price = l_items[l_idx].quantity * l_items[l_idx].unit_price
            DISPLAY l_items[l_idx].total_price TO s_items[scr_line()].total_price

        ON CHANGE quantity, unit_price
            LET l_idx = arr_curr()
            LET l_items[l_idx].total_price = l_items[l_idx].quantity * l_items[l_idx].unit_price

        BEFORE INSERT
            LET l_idx = arr_curr()
            LET l_items[l_idx].item_num = l_items.getLength() + 1

        AFTER DELETE
            CALL renumber_items(l_items)

        ON ACTION recalculate
            CALL calculate_grand_total(l_items)

    END INPUT
END FUNCTION
```

##### Ordre d'exécution des blocs de contrôle dans un tableau :
1. `BEFORE INPUT` / `BEFORE DISPLAY` : Initialisation générale du dialogue.
2. `BEFORE ROW` : Déclenché lorsque le focus arrive sur une nouvelle ligne.
3. `BEFORE FIELD` / `ON CHANGE` / `AFTER FIELD` : Séquence d'entrée et de validation sur chaque champ.
4. `ON ROW CHANGE` : Exécuté lorsque l'utilisateur modifie une ligne et tente de changer de rangée.
5. `AFTER ROW` : Déclenché à la sortie de la ligne courante.
6. `AFTER INPUT` / `AFTER DISPLAY` : Clôture du bloc interactif lors de la validation (`ACCEPT`) ou de l'annulation (`CANCEL`).

#### 1.2 Le Composant `CONSTRUCT` (Query-By-Example)

L'instruction `CONSTRUCT` transforme un écran de saisie en masque de recherche. Elle capture les critères saisis par l'utilisateur (valeurs exactes, intervalles `100..500`, masques `*ABC*`, opérateurs de comparaison) et génère dynamiquement une clause SQL `WHERE`.

```4gl
FUNCTION query_customers()
    DEFINE l_where_clause STRING
    DEFINE l_query_stmt STRING

    CONSTRUCT BY NAME l_where_clause ON customer_id, company_name, city, credit_limit

        BEFORE CONSTRUCT
            MESSAGE "Saisissez vos critères de recherche (ex: >1000, 'A*')"

        ON ACTION default_query
            LET l_where_clause = " credit_limit > 5000 AND status = 'A'"
            EXIT CONSTRUCT

    END CONSTRUCT

    IF int_flag THEN
        LET int_flag = FALSE
        RETURN
    END IF

    -- Construction de la requête SQL dynamique sécurisée
    LET l_query_stmt = "SELECT * FROM customer WHERE ", l_where_clause CLIPPED, " ORDER BY company_name"
    CALL execute_customer_search(l_query_stmt)
END FUNCTION
```

#### 1.3 Le Bloc Unifié `DIALOG` (Multiple Dialogs)

Historiquement, l'enchaînement de plusieurs masques imposait d'imbriquer des boucles ou des sous-programmes. Genero BDL introduit le bloc d'instruction unifié `DIALOG`, capable de gérer simultanément plusieurs sous-dialogues (`INPUT`, `DISPLAY ARRAY`, `INPUT ARRAY`, `CONSTRUCT`) dans une unique boucle d'événements.

```4gl
-- Gestion maître-détail unifiée dans un seul bloc DIALOG
FUNCTION manage_order_entry(p_order_id INT)
    DEFINE l_order RECORD LIKE orders.*
    DEFINE l_items DYNAMIC ARRAY OF RECORD LIKE order_items.*

    CALL load_order_header(p_order_id) RETURNING l_order
    CALL load_order_details(p_order_id) RETURNING l_items

    DIALOG ATTRIBUTES(UNBUFFERED = TRUE)

        -- Sous-dialogue 1 : En-tête de commande
        INPUT BY NAME l_order.customer_id, l_order.order_date, l_order.status
            ON CHANGE customer_id
                CALL update_customer_info(l_order.customer_id)
        END INPUT

        -- Sous-dialogue 2 : Lignes de commande
        INPUT ARRAY l_items FROM s_items.*
            BEFORE INSERT
                LET l_items[arr_curr()].order_id = l_order.order_id
        END INPUT

        -- Événements globaux partageant le contexte des deux sous-dialogues
        ON ACTION save
            IF validate_order(l_order, l_items) THEN
                CALL save_order_to_db(l_order, l_items)
                ACCEPT DIALOG
            END IF

        ON ACTION cancel
            EXIT DIALOG

    END DIALOG
END FUNCTION
```

### 2. Accès Données Avancé & Transactions SQL

En BDL, l'accès à la base de données s'appuie sur le moteur **ODI** (*Open Database Interface*), offrant une abstraction d'accès indépendante du SGBD (Informix, PostgreSQL, Oracle, SQL Server).

#### 2.1 Curseurs SQL et Manipulation de Jeux de Résultats

Lorsque les requêtes renvoient plusieurs lignes, l'utilisation des curseurs est obligatoire.

| Type de Curseur | Syntaxe Clé | Usage Métier |
| :--- | :--- | :--- |
| **Curseur de Lecture Simple** | `DECLARE` ... `CURSOR FOR` / `FOREACH` | Parcours séquentiel de données pour rapport ou remplissage de tableau. |
| **Curseur de Mise à Jour** | `DECLARE` ... `FOR UPDATE` | Verrouillage ciblé de lignes avant modification via `UPDATE ... WHERE CURRENT OF`. |
| **Curseur d'Insertion (Insert Cursor)** | `DECLARE` ... `INSERT INTO` + `PUT` / `FLUSH` | Performance extrême lors d'insertions massives par lots (*bulk insertion*). |

```4gl
-- Exemple de curseur d'insertion haute performance (Insert Cursor)
FUNCTION bulk_insert_logs(p_logs DYNAMIC ARRAY OF log_record)
    DEFINE i INT
    
    DECLARE c_ins CURSOR FOR 
        INSERT INTO app_audit_log (log_date, user_id, action_code, details)
        VALUES (?, ?, ?, ?)

    OPEN c_ins
    BEGIN WORK
    FOR i = 1 TO p_logs.getLength()
        PUT c_ins FROM p_logs[i].log_date, p_logs[i].user_id, p_logs[i].action_code, p_logs[i].details
        
        -- Vidage périodique du tampon mémoire vers la base
        IF i MOD 500 = 0 THEN
            FLUSH c_ins
        END IF
    END FOR
    
    FLUSH c_ins
    COMMIT WORK
    CLOSE c_ins
    FREE c_ins
END FUNCTION
```

#### 2.2 Concurrence, Verrouillage et Transactions ACID

Pour maintenir l'intégrité des données en environnement multi-utilisateurs, la gestion des verrous et l'isolation des transactions doivent être strictly contrôlées.

- **`SET LOCK MODE TO WAIT [seconds]`** : Définit le comportement du programme face à une ressource verrouillée par une autre session.
- **`SET ISOLATION TO ...`** : Configure le niveau d'isolation transactionnelle (`COMMITTED READ`, `CURSOR STABILITY`, `REPEATABLE READ`).
- **`BEGIN WORK` / `COMMIT WORK` / `ROLLBACK WORK`** : Délimitent le bloc transactionnel ACID.
- **`SAVEPOINT` / `RELEASE SAVEPOINT`** : Permettent des annulations partielles au sein d'une transaction complexe.

```4gl
-- Gestion transactionnelle robuste avec gestion d'erreurs et verrouillage
FUNCTION transfer_funds(p_src_acc INT, p_dest_acc INT, p_amount DECIMAL(12,2)) RETURNS BOOLEAN
    WHENEVER ERROR CONTINUE
    
    -- Attendre au maximum 10 secondes le déverrouillage d'une ligne
    SET LOCK MODE TO WAIT 10
    
    BEGIN WORK
        -- Verrouillage exclusif de la ligne source via SELECT FOR UPDATE
        DECLARE c_src CURSOR FOR 
            SELECT balance FROM account WHERE account_id = p_src_acc FOR UPDATE
        
        OPEN c_src
        FETCH c_src INTO l_balance
        
        IF status != 0 OR l_balance < p_amount THEN
            ROLLBACK WORK
            CLOSE c_src
            RETURN FALSE
        END IF

        UPDATE account SET balance = balance - p_amount WHERE account_id = p_src_acc
        IF status != 0 THEN
            ROLLBACK WORK
            CLOSE c_src
            RETURN FALSE
        END IF

        UPDATE account SET balance = balance + p_amount WHERE account_id = p_dest_acc
        IF status != 0 THEN
            ROLLBACK WORK
            CLOSE c_src
            RETURN FALSE
        END IF

    COMMIT WORK
    CLOSE c_src
    RETURN TRUE
END FUNCTION
```

### 3. Architecture Modulaire & Encapsulation

Le développement d'applications d'entreprise volumineuses nécessite de structurer le code en bibliothèques réutilisables et indépendantes.

#### 3.1 Fin des `GLOBALS` et Adoption d' `IMPORT FGL`

Les anciennes pratiques héritées d'Informix-4GL utilisaient abondamment les fichiers de variables globales (`GLOBALS`). En BDL moderne, les `GLOBALS` sont fortement déconseillés au profit de la **modularité orientée paquetages** (*Encapsulation*).

- **`PACKAGE`** : Définit l'espace de noms d'une bibliothèque (`package com.company.utils`).
- **`IMPORT FGL`** : Charge un module ou un paquetage compilé (`IMPORT FGL com_db_helper`).
- **`PUBLIC` / `PRIVATE`** : Contrôle la visibilité des variables, types et fonctions au niveau du module.

```4gl
-- Fichier: src/services/CustomerService.4gl
PACKAGE com.enterprise.services

-- Type public accessible par les modules importateurs
PUBLIC TYPE CustomerDTO RECORD
    id INT,
    name STRING,
    status CHAR(1)
END RECORD

-- Variable privée au module (encapsulée)
PRIVATE DEFINE m_cache_count INT = 0

-- Fonction publique (API du module)
PUBLIC FUNCTION get_customer(p_id INT) RETURNS CustomerDTO
    DEFINE l_cust CustomerDTO
    CALL internal_logging("Requête client: " || p_id)
    SELECT id, name, status INTO l_cust.* FROM customer WHERE id = p_id
    RETURN l_cust
END FUNCTION

-- Fonction privée interne non visible de l'extérieur
PRIVATE FUNCTION internal_logging(p_msg STRING)
    LET m_cache_count = m_cache_count + 1
    DISPLAY "[LOG] ", p_msg
END FUNCTION
```

#### 3.2 Structuration Moderne de la Gestion des Erreurs

Le mécanisme d'exception moderne repose sur les blocs `TRY ... CATCH`, remplaçant avantageusement le contrôle manuel systématique de la variable globale `status` ou `SQLCA.sqlcode`.

```4gl
FUNCTION execute_business_process()
    TRY
        BEGIN WORK
        CALL process_payment()
        CALL update_inventory()
        COMMIT WORK
        MESSAGE "Processus exécuté avec succès."
    CATCH
        ROLLBACK WORK
        -- Extraction des détails de l'exception
        CALL log_system_error(status, SQLCA.sqlerrd[2], status_message())
        ERROR "Échec de l'opération : ", status_message()
    END TRY
END FUNCTION
```

## Partie 2 : Niveau Senior (Architecte / Lead Tech)

Le niveau Senior requiert une vision globale de l'architecture logicielle : contrôle fin du moteur d'affichage AUI, exposition de Web Services enterprise, intégration JSON/XML et conception orientée performance et sécurité.

### 4. Manipulation Programmatique de l'IHM via l'AUI Tree

L'IHM de Genero repose sur le concept révolutionnaire de l'**AUI Tree** (*Abstract User Interface*). Le moteur d'exécution (DVM) maintient en mémoire un arbre XML représentant l'intégralité de l'interface utilisateur (fenêtres, formulaires, champs, menus, boutons).

```
[AUI Root Node: Interface]
   └── [Window Node]
        └── [Form Node]
             └── [Grid Container Node]
                  ├── [FormField Node: customer_id]
                  └── [Button Node: btn_submit]
```

#### 4.1 Manipulation du DOM AUI via les Classes `om.DomNode` et `ui.*`

Au niveau Senior, le développeur ne se contente pas de masques statiques ; il modifie la structure, l'apparence et le comportement de l'IHM dynamiquement à l'exécution en manipulant les nœuds DOM de l'AUI.

```4gl
-- Masquage ou modification dynamique de composants GUI via l'AUI Tree
FUNCTION customize_form_dynamically(p_user_role STRING)
    DEFINE l_win ui.Window
    DEFINE l_form ui.Form
    DEFINE l_win_node om.DomNode
    DEFINE l_node_list om.NodeList
    DEFINE i INT

    -- Obtenir la fenêtre courante et son nœud DOM d'origine
    LET l_win = ui.Window.getCurrent()
    LET l_win_node = l_win.getNode()

    -- Recherche XPath dans l'arbre AUI pour localiser tous les champs marqués 'restricted'
    LET l_node_list = l_win_node.selectByXPath("//FormField[@userTag='restricted']")

    FOR i = 1 TO l_node_list.getLength()
        IF p_user_role != "ADMIN" THEN
            -- Modification directe de l'attribut DOM pour désactiver le champ
            CALL l_node_list.item(i).setAttribute("active", "0")
            CALL l_node_list.item(i).setAttribute("style", "disabled_field")
        END IF
    END FOR
END FUNCTION
```

### 5. Services Web (SOA) & Architecture RESTful / JSON

Le framework **GWS** (*Genero Web Services*) permet à une application BDL de fonctionner comme serveur d'API REST/SOAP ou comme consommateur de services tiers.

#### 5.1 Exposition d'une API RESTful avec Annotations Native BDL

Genero BDL permet de déclarer des Web Services haut niveau directement via des attributs annotés dans le code source 4GL, générant automatiquement les spécifications **OpenAPI / Swagger**.

```4gl
-- Module Serveur REST API : ClaimService.4gl
IMPORT FGL gws

-- Configuration du service REST au niveau du module
ATTRIBUTES(
    WSInfo = "API REST de Gestion des Sinistres",
    WSVersion = "1.0",
    WSScope = "Public"
)

PUBLIC TYPE ClaimResponse RECORD
    claim_id INT,
    policy_number STRING,
    amount DECIMAL(10,2),
    status STRING
END RECORD

-- Exposition d'une opération HTTP GET
PUBLIC FUNCTION get_claim_by_id(p_claim_id INT ATTRIBUTES(WSParam, WSDescription="Identifiant unique du sinistre"))
    RETURNS ClaimResponse ATTRIBUTES(
        WSGet, 
        WSPath = "/api/v1/claims/{p_claim_id}",
        WSSummary = "Récupère les détails d'un sinistre"
    )
    
    DEFINE l_res ClaimResponse
    
    SELECT claim_id, policy_number, amount, status 
      INTO l_res.* 
      FROM insurance_claim 
     WHERE claim_id = p_claim_id
     
    IF status != 0 THEN
        -- Gestion des codes retours HTTP d'erreur
        CALL gws.set_http_status_code(404, "Sinistre non trouvé")
        RETURN NULL
    END IF

    RETURN l_res
END FUNCTION
```

#### 5.2 Traitement des Données Structurées (`util.JSONObject` & `om.XmlDocument`)

Pour manipuler des payloads complexes, BDL fournit des classes natives dédiées au parsing et au sérialisage JSON/XML.

```4gl
-- Manipulation native de JSON complexes
FUNCTION parse_external_json_payload(p_json_str STRING)
    DEFINE l_json_obj util.JSONObject
    DEFINE l_items_arr util.JSONArray
    DEFINE l_item_obj util.JSONObject
    DEFINE i INT

    LET l_json_obj = util.JSONObject.parse(p_json_str)

    IF l_json_obj.has("customer_name") THEN
        DISPLAY "Client : ", l_json_obj.get("customer_name")
    END IF

    -- Extraction d'un tableau JSON imbriqué
    LET l_items_arr = l_json_obj.getJSONArray("items")
    FOR i = 1 TO l_items_arr.getLength()
        LET l_item_obj = l_items_arr.getJSONObject(i - 1)
        DISPLAY "Produit : ", l_item_obj.get("product_code"), " Qté : ", l_item_obj.get("qty")
    END FOR
END FUNCTION
```

### 6. Design Patterns, Performance & Architecture Enterprise

#### 6.1 Le Pattern MVC (Modèle-Vue-Contrôleur) Strictement Appliqué à Genero

Pour assurer la pérennité des applications d'entreprise, l'architecture doit respecter une séparation stricte des responsabilités :

1. **Modèle (`.4gl`)** : Logique métier, requêtes SQL, validation des règles de gestion, indépendant de tout écran.
2. **Vue (`.per` / `.4fd`)** : Fichiers de formulaires définissant la mise en page visuelle et les composants UI.
3. **Contrôleur (`.4gl`)** : Instructions interactives (`DIALOG`, `INPUT ARRAY`, `ON ACTION`) liant le Modèle à la Vue sans embarquer de code SQL direct.

#### 6.2 Bilan Synthétique des Compétences par Niveau

```
[Junior]
 ├── Syntaxe de base, variables simples, boucles IF/FOR/WHILE
 ├── Requêtes SQL Statiques (SELECT simple, INSERT, UPDATE, DELETE)
 └── Formulaires statiques simples (DISPLAY TO, INPUT BY NAME)

[Middle / Intermediate]
 ├── Tableaux dynamiques (DISPLAY ARRAY, INPUT ARRAY)
 ├── Dialogues complexes (Bloc unifié DIALOG, CONSTRUCT / Query-By-Example)
 ├── Curseurs SQL (FOR UPDATE, INSERT Cursors) & Transactions ACID
 └── Modularité moderne (IMPORT FGL, PACKAGE, PUBLIC/PRIVATE, TRY...CATCH)

[Senior / Lead Tech / Architecte]
 ├── Manipulation de l'AUI Tree via DOM (om.DomNode, XPath)
 ├── Services Web SOA & RESTful APIs (Framework GWS, OpenAPI/Swagger)
 ├── Parsing JSON/XML avance (util.JSONObject, om.XmlDocument)
 └── Architectural Patterns (MVC strict, Tuning SQL/Performance, Multi-déploiement GWC/GDC)
```

## Directives d'Exécution pour les Projets d'Envergure

1. **Bannir les Variables Globales** : Remplacer systématiquement les blocs `GLOBALS` par des modules encapsulés avec types et fonctions `PUBLIC`.
2. **Systématiser la Gestion des Erreurs** : Encadrer tous les traitements critiques et SQL transactionnels dans des structures `TRY ... CATCH`.
3. **Séparer Strictement le Code SQL et l'IHM** : Ne jamais exécuter de requêtes SQL directes à l'intérieur des blocs événementiels `ON ACTION` d'un formulaire ; déléguer systématiquement aux fonctions du Modèle métier.
4. **Préférer le Bloc `DIALOG` Unifié** : Privilégier la structure `DIALOG` multi-sous-dialogues pour la gestion des écrans complexes Maître-Détail afin de rationaliser le flux événementiel.
